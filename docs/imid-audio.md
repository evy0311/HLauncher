# i-MID audio information while HondaLink Apps is selected

The owner reports that the i-MID audio page shows **Apps** with a blank content
area while HondaLink/HLauncher is open. This trace checks the decrypted Connect
IPA, the stock Civic radio firmware, and HLauncher's current metadata handling.
No phone-to-i-MID song-text command has been established for this source mode.

## Findings at a glance

| Path | Evidence | What it establishes |
| --- | --- | --- |
| Connect JavaScript audio API | `honda.audio.playAudio`, `stopAudio`, audio-state and mute listeners | On iOS, playback uses a JavaScript Audio object. There is no exposed title/artist/album publishing function in the inspected SDK inventory. |
| Connect native audio layer | `HLAudio` and `HLJsAudio` | Observes notifications and forwards mute state into the WebView. The inspected handlers do not emit HondaLink track metadata. |
| Firmware AppMode display data | `RN_ExtDispAppMode`, Communication.exe publishers `0x51148/0x511C4` | Two status publications, each containing three one-byte scalar values; no string arguments in those publishers. |
| Bluetooth AVRCP | Existing HLauncher `AvrcpTarget` | A distinct metadata channel with title/artist/album response support. This does not establish that the radio uses it for the Apps i-MID page. |
| HLauncher radio metadata policy | `media.radio_metadata()` and controls-worker `metadata()` | AVRCP serves the selected projection's title, artist and album when reported, or the source label (such as **CarPlay**) when a title is unavailable. |

The external-display model also names BTA, iPod, USB, CD and Pandora branches.
Their presence does not establish that Bluetooth/iPod text is merged into the
AppMode branch. Some names describe generated shared schemas rather than a
proven physical output route. The final i-MID/MCU rendering behavior remains
outside the traced AppMode publisher chain.

## Decrypted IPA: what the inspected audio code actually does

Native addresses refer to Connect 1.0.0 ARMv7, SHA-256
`8b957d788de6ff3e8ba975cb7d34d5bfbe1987d56be4d4666869b766da154aae`.
The JavaScript SDK inventories cover the five Connect versions 1.0.0–1.3.1.

- `honda.audio.playAudio(url, callback)` takes a URL. Its iOS branch sets an
  HTML Audio object's source and plays it; its Android branch uses the local
  `AudioControl/PlayAudio` bridge. Neither is a recovered radio title message.
- `honda.audio.stopAudio` pauses that object on iOS.
- Audio-state listeners attach browser playback events on iOS. Mute listeners
  are separate callbacks.
- `HLAudio.init` at `0x636F0` registers an NSNotificationCenter observer for
  `onAudioStateChanged:`.
- `HLAudio.onAudioStateChanged:` at `0x637C8` reads notification userInfo and
  invokes its delegate's `onMuteStateChanged:` with a boolean.
- `HLJsAudio.onMuteStateChanged:` at `0x3B3A8` calls
  `sendHondaNativeEvent:name:value:` with event **501**, name `isMute`, and a
  boolean string. This is a native-to-WebView event, not wire opcode 501.

No title/artist/album publishing API, MPNowPlayingInfo-style selector, or explicit
HondaLink now-playing send method was identified in the inspected Connect SDK
and Objective-C metadata. This is a scoped negative finding, not proof that no
version, separate music app, dynamically invoked function or iOS media service
can ever provide metadata. Connect is not the separate Aha music app. Normal
Bluetooth/iPod metadata generated by iOS or a music application is a separate
path from these HondaLink application messages.

## Firmware: AppMode publishes status bytes

The stock Civic Communication.exe baseline has SHA-256
`cdda1bcc4d53e08087899faef7be1512baa563098c1603496384612e435b1f43`.

Its generated `RN_ExtDispAppMode` schema has group `0x44`, with members
`0x44000000`, `0x44010000`, `0x44020000`, `0x44030000`. These are internal RN
identifiers, not HondaLink message IDs or CAN arbitration IDs.

Two publishers are concretely used:

```text
AppMode state conversion at 0xB3C60
 -> wrapper 0xB1128 or 0xB1178
 -> publisher 0x51148 or 0x511C4
 -> RNCommLib transport
```

The wrappers check a connection-related condition through `0x7DE4C` and pass
three scalar arguments. The publishers build RN member `0x44000000` or
`0x44020000`, append all three arguments with RNCommLib ordinal 124, and send.
Ordinal 124 resolves through `0x41B21F38` to `0x41B234AC`, which stores its
argument with a byte write before handing it to the underlying serializer.
Thus these are **three one-byte status values**, not title/artist strings or
pointers to strings. State conversion includes values such as `0xD0`, `0xF1`
and `0xF4`; their entire user-facing vocabulary has not been decoded.

Initial AppMode setup at `0xB4154` calls the wrapper with `0xD0, 0`; later
state conversion changes the compact status representation. This is consistent
with a source/status-only display while Apps is active, but it does not by
itself identify the MCU's literal “Apps” label or prove that its blank area is
hardcoded. The final display consumer and any alternate metadata source still
need tracing. No supported string setter was recovered from this chain.

The `RN_ExtDisp` model also has source-specific groups: AudioFile `0x37`,
VideoFile `0x38`, BTA `0x39`, CD `0x3A`, DiskDevice `0x3B`, DVD `0x3C`, iPod
`0x3D`, Pandora `0x3E`, USBDevice `0x3F`, and MirrorLink `0x45`. These separate
groups are a reason to test source selection rather than assuming all audio
modes share their metadata. Their schemas alone are not evidence of arbitrary
text support for AppMode.

`UICommMain_SenderForSubDisplay` was also inspected. A class name containing
“SubDisplay” is insufficient to identify a now-playing text path; it must not
be used as evidence that song metadata reaches this audio page.

## Source selection and HLauncher metadata

The CarPlay bridge handles dongle MediaData USB type `0x2A`, subtype `1`.
The host requests dashboard reports from the adapter via BoxSettings. Song, artist and album
fields feed the host's now-playing broker when the adapter supplies them.
The AVRCP target answers GetElementAttributes and sends subscribed track-change
notifications. Its fallback is available even if the dongle reports no song.

A follow-up scan found direct code references to the AppMode RN publication IDs
`0x44000000` and `0x44020000` only at the two Communication.exe publishers above.
AV.exe separately implements `AudioSourceAppMode` (vtable `0xC5BB4`) and Bluetooth
audio status objects (`AVMsg_RNBTAudioStatusInfoSTDLong` and `STDShort`, vtables
`0xC7BD4` and `0xC7B44`). The Bluetooth module also exposes AVRCP attribute APIs
such as `BTAVRCP_CtGetItemAttributes`. These are separate source paths. The
traced Apps publishers have no track string to forward, and no bridge from
Bluetooth metadata into that Apps publication was identified. The final i-MID
rendering path and whether a specific firmware revision queries AVRCP while
Apps is selected still need hardware verification.

## Useful next experiment

A bounded metadata-only test can determine whether AVRCP supplies the blank
area **without switching out of Apps or changing the audio route**:

1. Capture AVRCP GetElementAttributes (`0x20`), track-change subscription and
   continuation (`0x40/0x41`), and any iAP lingo-4 metadata queries, with the
   current source and i-MID page noted.
2. Under an explicit temporary test mode, publish unmistakable test labels
   through the existing AVRCP responder and issue its normal track-change
   notification. Avoid inventing a HondaLink text opcode.
3. Observe whether the radio fetches the fields and whether either display
   changes while Apps remains active. No query, a returned response, and text
   actually appearing are three different outcomes.
4. Compare the result with Bluetooth Audio selected. A radio-side source mapping
   would need to supply Apps text if the stock i-MID ignores the AVRCP reply.

This test has not been performed in this trace. Real song availability from
CarPlay/Android Auto also depends on what their projection bridges report; a
local SDK publishing API does not guarantee those plugins supply every field.
The recovered meter-guidance CAN transmit path is unrelated and is not a
workaround for missing Apps audio metadata.
